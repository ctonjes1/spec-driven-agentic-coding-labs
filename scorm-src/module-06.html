Module 6 Human Review Staging Worker for Project Updates

.NET and Azure production systems

45–60 minute labsClaude Code and CodexEvidence required
Specification gate: finish and freeze SPEC.md and its acceptance criteria before creating implementation files.

Objective

Stage transcript-derived project updates for review without directly changing the authoritative project record.

Human judgment

Explain why preserved provenance does not prove that an extracted project statement is accurate.

Constraints

  1. .NET worker with in-memory adapters
  2. No live meeting transcript or resident data
  3. At-least-once delivery is assumed
  4. Only a human can approve promotion

Threat and failure assumptions

  1. A message is redelivered
  2. The source version is stale
  3. Storage fails before message settlement
  4. Narrative content leaks into operational logs

Frozen contract

Write these numbered requirements into SPEC.md. Add exact schemas, reason codes, precedence, error behavior, trust boundaries, and requirement-to-test traceability. Mark the reviewed contract SPEC STATUS: FROZEN and SPEC VERSION: 1.0.

  1. R1 Validate source ID, version, digest, and correlation ID
  2. R2 Store a pending proposal before completing the message
  3. R3 Treat same-message replay as idempotent
  4. R4 Quarantine conflicting digests or stale source versions
  5. R5 Never write directly to the authoritative record
  6. R6 Complete, abandon, or dead-letter messages by documented outcome
  7. R7 Log identifiers, state, and reason without narrative text

Acceptance criteria

  1. Valid message creates one pending proposal
  2. Identical redelivery creates no duplicate
  3. Changed digest with same message ID conflicts
  4. Stale project version is quarantined
  5. Storage failure prevents message completion
  6. Invalid schema is dead-lettered
  7. No path promotes without human approval
  8. Logs contain no transcript narrative

Implementation checkpoints

TimeRequired activity
0–12 minutesClaude Code drafts SPEC.md and acceptance criteria. Codex challenges ambiguity, unsafe defaults, precedence, and unverifiable claims. The learner resolves findings and freezes version 1.0. No implementation files exist yet.
12–23 minutesCodex derives black-box tests from the frozen contract and captures the expected failing run. Claude Code identifies contradictions without silently rewriting tests or requirements.
23–41 minutesClaude Code implements only frozen requirements and updates the requirement-linked change ledger. Preserve the complete test output.
41–53 minutesCodex reviews the diff against SPEC.md, reruns tests independently, exercises the adversarial path, and inspects logs, errors, dependencies, and state transitions.
53–60 minutesThe learner records the human disposition, remaining assumptions, production gaps, and an evidence-bounded completion statement.

Required adversarial or failure-path test

Inject a storage failure immediately before save and redeliver the message. The worker must not settle the first delivery and must create at most one pending proposal after recovery.

Evidence package

Module-specific evidence: Storage-failure injection, settlement sequence, redelivery test, stale-version result, and narrative-leakage check.

Also submit SPEC.md, README.md, TRACEABILITY.md, a requirement-linked change ledger, source and tests, initial failing output, final complete output, review findings, and an evidence-bounded completion statement.

Knowledge check and evidence attestation

1. When may the worker complete a message?
2. Where should extracted updates go?
3. What should an identical redelivery do?
4. What does provenance establish?
