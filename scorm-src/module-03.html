Module 3 Idempotent Azure Ready Intake API

.NET and Azure production systems

45–60 minute labsClaude Code and CodexEvidence required
Specification gate: finish and freeze SPEC.md and its acceptance criteria before creating implementation files.

Objective

Implement the core of an intake endpoint that validates requests, rejects conflicting replays, and returns stable results.

Human judgment

Identify the durable storage, transaction, and distributed-concurrency controls still required for production.

Constraints

  1. ASP.NET Core minimal API with in-memory storage
  2. No cloud deployment or external database
  3. Idempotency key is required
  4. Request bodies and secrets never enter logs

Threat and failure assumptions

  1. A client retries after a timeout
  2. The same key arrives with an altered payload
  3. Two requests race for the same key
  4. A storage failure occurs after validation

Frozen contract

Write these numbered requirements into SPEC.md. Add exact schemas, reason codes, precedence, error behavior, trust boundaries, and requirement-to-test traceability. Mark the reviewed contract SPEC STATUS: FROZEN and SPEC VERSION: 1.0.

  1. R1 Validate input before reserving an idempotency key
  2. R2 Canonicalize the accepted request and calculate a stable digest
  3. R3 Return the original result for an identical replay
  4. R4 Return 409 for the same key with a different digest
  5. R5 Avoid a success response when persistence fails
  6. R6 Emit correlation ID, outcome, and reason without body content
  7. R7 Isolate storage behind a narrow interface

Acceptance criteria

  1. New valid request returns 202
  2. Identical replay returns the original result
  3. Altered replay returns 409
  4. Missing key returns 400
  5. Invalid payload creates no reservation
  6. Injected storage failure returns controlled 503
  7. Concurrent duplicate calls produce one accepted result
  8. Logs exclude request body and secrets

Required adversarial or failure-path test

Send two simultaneous requests with one idempotency key and different payloads. Exactly one digest may own the key; the other request must receive a conflict and no second work item may be created.

Evidence package

Module-specific evidence: Replay tests, altered-payload conflict, storage failure injection, concurrent result, stable digest, and dependency inspection.

Also submit SPEC.md, README.md, TRACEABILITY.md, a requirement-linked change ledger, source and tests, initial failing output, final complete output, review findings, and an evidence-bounded completion statement.
