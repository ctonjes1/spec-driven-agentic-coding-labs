Module 10 Approval Bound Agent Action Broker

Secure enterprise services and agents

45–60 minute labsClaude Code and CodexEvidence required
Specification gate: finish and freeze SPEC.md and its acceptance criteria before creating implementation files.

Objective

Bind human approval to the exact canonical action and prevent substitution, replay, or concurrent duplicate execution.

Human judgment

Identify the limits of local replay controls and the crash-after-side-effect problem.

Constraints

  1. Synthetic side effects only
  2. Approval tokens are opaque and never logged
  3. Prepare and commit are separate operations
  4. Executor calls are recorded by digest and result

Threat and failure assumptions

  1. Action changes after approval
  2. Approval token is replayed
  3. Two workers commit concurrently
  4. A crash follows the external side effect but precedes local completion

Frozen contract

Write these numbered requirements into SPEC.md. Add exact schemas, reason codes, precedence, error behavior, trust boundaries, and requirement-to-test traceability. Mark the reviewed contract SPEC STATUS: FROZEN and SPEC VERSION: 1.0.

  1. R1 Canonicalize the complete proposed action before approval
  2. R2 Bind approval to action digest, actor, expiry, and nonce
  3. R3 Reject changed, expired, or reused approval
  4. R4 Atomically claim an idempotency key before executor invocation
  5. R5 Allow at most one executor call per committed action
  6. R6 Preserve PREPARED, CLAIMED, SUCCEEDED, FAILED, and UNKNOWN states
  7. R7 Redact approval tokens and action payloads from logs

Acceptance criteria

  1. Prepared action receives a stable digest
  2. Matching approval commits once
  3. Altered action is rejected
  4. Expired approval is rejected
  5. Replay returns the recorded result
  6. Concurrent commit invokes executor once
  7. Executor failure records FAILED
  8. Crash-after-side-effect records UNKNOWN for reconciliation

Implementation checkpoints

TimeRequired activity
0–12 minutesClaude Code drafts SPEC.md and acceptance criteria. Codex challenges ambiguity, unsafe defaults, precedence, and unverifiable claims. The learner resolves findings and freezes version 1.0. No implementation files exist yet.
12–23 minutesCodex derives black-box tests from the frozen contract and captures the expected failing run. Claude Code identifies contradictions without silently rewriting tests or requirements.
23–41 minutesClaude Code implements only frozen requirements and updates the requirement-linked change ledger. Preserve the complete test output.
41–53 minutesCodex reviews the diff against SPEC.md, reruns tests independently, exercises the adversarial path, and inspects logs, errors, dependencies, and state transitions.
53–60 minutesThe learner records the human disposition, remaining assumptions, production gaps, and an evidence-bounded completion statement.

Required adversarial or failure-path test

Approve one canonical action, then change a recipient field and race two commit calls using the same token. The changed action must fail and the executor call history must show no more than one invocation.

Evidence package

Module-specific evidence: Canonicalization tests, altered-action conflict, concurrent commit result, executor call history, and approval-token leakage inspection.

Also submit SPEC.md, README.md, TRACEABILITY.md, a requirement-linked change ledger, source and tests, initial failing output, final complete output, review findings, and an evidence-bounded completion statement.

Knowledge check and evidence attestation

1. What must approval bind to?
2. When should the broker claim the idempotency key?
3. What state fits an uncertain crash after a side effect?
4. How many executor calls may a committed action produce?
